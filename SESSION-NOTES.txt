PROJECT OVERVIEW
===================
Trellis is an AI-assisted, monday.com-style work management SaaS,
purpose-built for client-facing teams — agencies, consultancies,
studios, and professional-services firms whose work is ultimately
delivered to someone outside the company. One-liner from the blueprint:
"the AI-assisted work operating system for client-facing teams — plan
work, run it, and show it to clients without ever exporting a
spreadsheet."

Like monday.com, the product is built around colorful, customizable
boards: groups, items, typed columns, multiple views, automations, and
dashboards. Unlike monday.com's horizontal "Work OS for everyone"
positioning, Trellis is deliberately narrower — it bets on one
underserved job (external, client-facing collaboration) rather than
trying to be everything to every team.

The product is currently free — no billing, subscriptions, or paywalls
exist anywhere in the codebase, and none are planned until well past
the phases covered here (see Scope, below).


BACKGROUND
============
The project started as a full four-stage product blueprint (11
documents in /docs, 00-index.md onward), written before any code
existed: vision & scope, data model, backend architecture, API design,
automation engine, frontend architecture, UX flows, roadmap,
differentiation/AI strategy, security/compliance, and — added during
this implementation session — a UI/UX design system spec
(docs/11-ui-design-system.md). Every decision below traces back to that
blueprint rather than being invented ad hoc.

One notable revision made to the original blueprint, on the same day it
was completed: AI was reclassified from a deferred/optional layer to a
core product pillar. This reversed an original non-goal and rippled
across every document — a fourth vision pillar ("AI-native, not
AI-bolted-on"), new AI feature tables in the phase breakdown, dedicated
AI database tables, an AI backend module, and AI-specific frontend
patterns (suggestion surfaces, never a bolted-on chatbot).

Four product pillars anchor every roadmap and design decision made
since:
  1. Client-grade by default — sharing with an outside client is a
     first-class flow, not a permissions workaround.
  2. Fast and keyboard-first — sub-100ms perceived interaction budget,
     full ⌘K command palette, no spinners on core actions.
  3. Transparent automations — every automation run is logged and
     debuggable; automations are never a "magic," opaque black box.
  4. AI-native, not AI-bolted-on — AI lives inside existing workflows
     (search, drafting, summarizing) and every AI action is a
     suggestion until a human confirms it — never an autonomous
     mutation, and never trained on client-portal/share-link data.

Actual implementation (the code in this repo) began after the blueprint
was complete: a backend "walking skeleton" (Fastify API + Drizzle ORM
against Postgres, with a Docker-free PGlite dev mode) and a React SPA
frontend were built to prove the core data flow end-to-end — auth, org,
workspace, board, groups, columns, items, column values — before any
UI polish was invested. This session's work (logged below) picks up
from that walking skeleton: first making it runnable, then building it
into a genuinely presentable product UI.


PROJECT OBJECTIVES
=====================
From the blueprint's stated vision, the objectives guiding the product
are:

  - Prove a board-based work management tool can feel faster and more
    pleasant to use than both a spreadsheet and monday.com itself.
  - Make sharing work with an external client a two-click, polished,
    first-class flow — not a bolted-on permissions hack — since serving
    outside stakeholders is the product's core wedge.
  - Weave AI into workflows users already rely on (search, drafting,
    catching up on a thread) rather than shipping a separate chatbot
    nobody opens; every AI action must be suggest -> review -> confirm,
    never autonomous.
  - Keep automations transparent and debuggable: every run logged with
    inputs, outputs, and failures, with dry-run preview before
    enabling.
  - Reach product-market signal in stages, each with a concrete exit
    gate (see Scope, below) before expanding further — not building V1
    features while still proving the MVP loop.
  - Stay free through the phases covered by the current blueprint,
    prioritizing adoption and the external-collaborator network effect
    over early monetization.

The immediate objective of this working session specifically was to
take the walking skeleton from "runs, barely" to a genuinely presentable
product: get it running locally, remove friction from iterating on it
(the dev auth bypass), design a real visual/interaction language for
it, and implement that design on the core surfaces (app shell, home,
board table, kanban, item detail) — all without exceeding the MVP
feature boundary the blueprint sets.


PROJECT SCOPE
================
The blueprint defines four phases, each with a stated goal and exit
criteria. This repository is currently being built to MVP scope only —
per CLAUDE.md, V1/V2/Enterprise features are explicitly out of bounds
even opportunistically, and anything not tagged MVP in the docs should
be treated as not yet in scope.

  Phase        Timeframe      Goal                                  Exit criteria
  -----        ---------      ----                                  -------------
  MVP          Months 0-4     Prove core board UX with design       20 design-partner teams;
                               partners                              >= 40% week-4 retention;
                                                                      item-edit p95 < 300ms
  V1           Months 5-9     Public launch, client-access wedge    500 weekly-active teams;
                                                                      >= 25% of active boards use
                                                                      a client share link/guest
  V2           Months 10-18   Scale, mobile, depth (workload,       5,000 weekly-active teams;
                               formulas, connect boards)             >= 40% month-3 retention
  Enterprise   Months 16-24   Deployable at 100+ seat orgs           SOC 2 Type II; 5 deployments
               (overlaps V2)  (still free — "readiness," not a       at 100+ seats; SSO/SCIM/
                               paid tier)                            audit GA

MVP scope (what this codebase is currently being built to) includes:
  - Auth: email+password, Google OAuth, optional TOTP 2FA; single
    workspace per account; admin/member roles.
  - Boards: main + private boards, groups, items, archive/delete with
    30-day recovery, batch edit up to 500 items.
  - 8 column types: status, text, long_text, number, person, date,
    dropdown, checkbox — with custom status labels and colors.
  - Views: Table (virtualized to 20k items) and Kanban only. Filters,
    3-key sort, saved views.
  - Collaboration: rich-text updates/comments with @mentions, activity
    logs, file attachments on updates.
  - Notifications: in-app + email.
  - Search: ⌘K palette with board jump, item search, and AI-assisted
    natural-language search.
  - AI: strictly limited to natural-language search and one-click
    thread summarization — every other AI feature (task generation,
    automation suggestions, project planning, dashboard insights,
    meeting-to-task, risk detection, the AI assistant) is V1 or later.
  - 6 starter board templates, CSV import/export, responsive mobile
    web, basic admin.

Explicitly NOT in MVP scope (deferred to V1 or later — do not build
opportunistically): subitems, folders, multiple workspaces,
Timeline/Gantt/Calendar views, forms, dashboards, the automations
engine, integrations beyond CSV, guest accounts/client share links,
public API/webhooks, time tracking, dependencies, recurring items,
teams/@team, global cross-workspace search, and PWA push.

Permanent, all-phase non-goals (never planned, any phase): a docs/wiki
editor, a whiteboard tool, a chat product, a full CRM or developer-grade
issue tracker, and self-hosted deployment — Trellis integrates with the
category leaders in those spaces instead of rebuilding them.

Constraint that applies across every phase covered by the current
blueprint: the product is free. No billing, subscription, plan-tier, or
payment code exists or is being built; `organizations.plan` is always
'free', and quota/rate limits that do exist (storage, automation runs,
API rate, etc.) are fair-use/abuse-prevention limits, not a pricing
mechanism.

--------------------

features could be tested without repeatedly authenticating, without
deleting the auth feature (auth is MVP scope per CLAUDE.md).

Decision: keep AuthPage/signup/login routes and code completely
intact; add a dev-only bypass instead of removing anything.

Backend fix found and fixed while wiring this up:
  Problem: logging in never bound a session to the user's organization
  — only creating or explicitly selecting an org did. Any brand-new
  browser session (including this test) landed on the "create
  organization" screen despite already having an org and seeded boards.
  Fix: apps/api/src/modules/auth/routes.ts — POST /auth/login now looks
  up the user's most recently active org from their session history and
  re-verifies membership through the tenant-scoped path (same check as
  the existing org-select endpoint) before adopting it into the new
  session.
  Added a regression test in auth.test.ts: "login resumes the user's
  most recent active organization." Full suite: 40/40 passing.
